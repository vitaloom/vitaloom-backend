# Heart Rate Data Model & Persistence Design

**Status:** Approved design baseline for the Heart Rate MVP
**Scope:** MongoDB measurement document, ownership, identity, indexes and retention
**Related API contract:** [Heart Rate metrics and ingestion](../api/api-contract.md#7-heart-rate-metrics--batch-ingestion)

This design is specific to Heart Rate. Steps has its own model, collection, repository and ingestion behavior; do not generalize both metrics into a shared event document or collection.

## 1. Design decisions

| Concern | Decision |
|---|---|
| Persistence unit | One MongoDB document per accepted measurement |
| Collection | `heart_rate_measurements` |
| Account ownership | `accountId` comes from the authenticated account context; it is never accepted from the request body |
| Device identity | Required `deviceId`, stable for one physical or simulated device across Producer runs |
| Measurement identity | Required `eventId`, generated once per measurement and reused on retries |
| Measurement value | Integer `heartRateBpm`, MVP sanity range 1–300 inclusive |
| Event time | `occurredAt`, represented as Java `Instant` and stored as a UTC BSON Date |
| Receipt time | `receivedAt`, assigned by Backend when the batch is received |
| Ordering | Out-of-order measurements and multiple measurements with the same `occurredAt` are allowed |
| Retention | Keep raw measurements for the MVP; no TTL index |

An event with `occurredAt` strictly later than the batch receipt instant is rejected item by item with `FUTURE_OCCURRED_AT`; there is no clock-skew grace period. The service captures one receipt instant for the batch. Before persistence, `occurredAt` is truncated to MongoDB BSON Date millisecond precision so retry comparison uses the same canonical value MongoDB stores.

The BPM range is an input sanity boundary only. It is not a definition of a normal, abnormal or clinically safe heart rate. Values inside the boundary are stored as received; the ingestion path does not reinterpret or silently normalize them.

## 2. MongoDB document

Collection: `heart_rate_measurements`

Example:

```json
{
  "_id": "ObjectId(...)",
  "accountId": "<authenticated-account-id>",
  "deviceId": "device-001",
  "eventId": "hr-run-001-000001",
  "heartRateBpm": 82,
  "occurredAt": "2026-11-05T12:30:15.000Z",
  "receivedAt": "2026-11-05T12:30:17.250Z"
}
```

| Field | BSON / Java type | Required | Owner / rule |
|---|---|---:|---|
| `_id` | ObjectId | Yes | Generated by MongoDB / Backend; internal document identity |
| `accountId` | Canonical Account ID type | Yes | Resolved from authenticated principal; BSON representation must match the Account model |
| `deviceId` | String | Yes | Comes from the batch envelope; stable for the device, not a Producer run |
| `eventId` | String | Yes | Unique measurement ID within an account/device; preserved for retries |
| `heartRateBpm` | Int32 / Java `int` | Yes | Integer from 1 through 300 inclusive |
| `occurredAt` | BSON Date / Java `Instant` | Yes | Source measurement time; normalized to millisecond precision for MongoDB persistence |
| `receivedAt` | BSON Date / Java `Instant` | Yes | Backend receipt time; one receipt instant is assigned to newly accepted items in the same batch |

### Fields intentionally not stored

- `runId` is batch/run diagnostic metadata. It is returned in the batch response and may appear in logs, but is not part of a measurement's identity or lifecycle.
- `source` is omitted because the current accepted source is the VitaLoom Data Producer. Add a source discriminator only when a second ingestion source is actually introduced.
- A derived `statisticsDate` is not stored. The statistics layer derives the local day from `occurredAt` using the current MVP timezone, `Asia/Ho_Chi_Minh`.
- No aggregate, average, minimum or maximum is stored in this raw collection.

The API carries `deviceId` once at the batch envelope; Backend copies it into each accepted measurement document. Device identity is a stable source identifier, not proof of device ownership or an authentication credential. The MVP does not introduce a Device collection or device-registration workflow.

The exact BSON type for `accountId` follows the canonical Account identifier when Authentication persistence is designed. Do not invent a separate Heart Rate account ID representation.

## 3. Indexes

Create only the following two indexes for the MVP.

### 3.1. Unique measurement identity

```javascript
db.heart_rate_measurements.createIndex(
  { accountId: 1, deviceId: 1, eventId: 1 },
  { unique: true, name: "uk_hr_account_device_event" }
)
```

This prevents the same measurement identity from being persisted twice for one account and device. All three fields are required, so no partial index is needed.

When a duplicate-key write occurs, the application reads the existing measurement and compares the immutable measurement payload:

- Same `occurredAt` and `heartRateBpm`: classify the incoming item as `DUPLICATE`.
- Different `occurredAt` or `heartRateBpm`: classify it as `REJECTED` with `EVENT_ID_CONFLICT`.

The comparison uses the timestamp normalized to MongoDB's millisecond precision. `receivedAt` and `runId` are not part of payload identity.

The same `eventId` under a different `deviceId` is a different measurement identity and is not deduplicated across devices.

### 3.2. Account history and daily aggregation

```javascript
db.heart_rate_measurements.createIndex(
  { accountId: 1, occurredAt: 1 },
  { name: "ix_hr_account_occurred_at" }
)
```

This supports the account-scoped time-range query used to read measurements for a statistics day. The query uses an inclusive start and exclusive end instant derived from the local day boundary in `Asia/Ho_Chi_Minh`.

Do not add indexes on `receivedAt`, `deviceId` alone, or additional sort combinations until a real query requires them.

## 4. Persistence and data rules

1. Persist only items accepted by Heart Rate validation.
2. Do not update an existing measurement when a new item arrives. A reused ID with changed measurement content is an ID conflict, not an update.
3. Do not reject a measurement because it arrives out of chronological order.
4. Do not use `occurredAt` as a unique key. Different measurements, including measurements from different devices, may share the same timestamp.
5. Generate `receivedAt` on the Backend. Never accept it from the Producer.
6. Keep accepted raw measurements as the source of truth. Daily Average is calculated from valid accepted measurements; it is not written back into this collection.
7. No TTL or scheduled raw-data deletion is introduced in the MVP. Revisit retention only after Statistics requirements, recalculation needs and actual storage volume are understood.

## 5. Raw query boundary and Statistics ownership

The Heart Rate feature owns raw measurement persistence and exposes raw-data query capabilities through its service. Statistics owns the calculations and derived response values.

The Heart Rate service exposes only the source data needed by Statistics:

- The latest accepted Heart Rate observation for an authenticated account, ordered by maximum `occurredAt`; ties use ascending lexical `deviceId`, then ascending lexical `eventId`.
- Accepted Heart Rate observations within a supplied half-open instant range `[start, end)`.

The Heart Rate service does not calculate Daily Average, Latest Recorded summary DTOs, time-bucketed aggregates or dashboard values. It does not own an aggregate/read-model persistence layer.

The Statistics feature uses those query capabilities to compose the Heart Rate summary:

- **Latest Recorded HR:** one accepted observation with the maximum `occurredAt` across the account's full history, independent of the selected statistics date. It returns BPM and the original measurement timestamp.
- **Daily Average HR:** the unweighted arithmetic mean of accepted BPM measurements whose `occurredAt` falls within the selected local calendar day, using the existing `Asia/Ho_Chi_Minh` half-open day boundaries.
- A day with no accepted observations returns `null` BPM, not zero.
- The selected `date` filters Daily Average only. It does not change Latest Recorded.
- Latest and Daily Average are calculated on read for the MVP. No aggregate collection, materialized read model, background aggregation pipeline or extra index is introduced for these values.

The API endpoint and response DTO belong to Statistics, even though the source observations are owned and queried by Heart Rate. The current summary endpoint is `GET /api/statistics/heart-rate/summary?date=YYYY-MM-DD`; its external behavior is defined in the [API Contract](../api/api-contract.md#7-heart-rate-metrics--batch-ingestion).

Statistics must not access the Heart Rate repository, Mongo document or collection directly. It obtains raw observations only through the Heart Rate service's query capabilities. Future aggregate persistence, if justified, is owned by Statistics under [ADR-001](./decisions/ADR-001-statistics-owns-aggregate-read-models.md).

## 6. Dependencies and explicit non-goals

- Basic Authentication is implemented. Heart Rate batch ingestion and the Statistics Heart Rate summary require a Bearer access JWT and scope records by its subject (`accountId`). Other metric endpoints and the cross-metric daily dashboard do not yet enforce equivalent per-user access and isolation.
- There is no Device registry in this design. Device registration, revocation, metadata and ownership verification are deferred.
- The current Producer represents one device. A future Producer load mode may start multiple device instances with different stable `deviceId` values and intervals. Worker count and load-generation controls are Producer concerns, not Heart Rate domain fields.
- HTTP request-level `Idempotency-Key` storage is not added. Measurement-level `eventId` plus the unique index is the MVP idempotency mechanism.
- This design does not define real wearable/Health API ingestion. A future source without stable event IDs needs a source-specific identity policy before it is integrated.
